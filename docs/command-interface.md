# Charme 命令交互、脚本与 AI 设计方向

本文档记录 Charme 关于 CAD 风格交互、命令行、脚本、C/S 架构和 AI Agent 的设计讨论。当前是方向性设计，尚不代表已经实现的 API 或协议。

## 目标

Charme 不只提供 GUI 操作，还应提供一种适合熟练用户、批处理和 AI 自动化的命令驱动体验：

- GUI、REPL、脚本和 AI 使用同一套编辑语义；
- 命令可以查询、预览、执行、撤销和重做；
- 脚本可以重复执行并纳入版本控制；
- AI 可以在权限和事务约束下辅助编辑；
- 未来可以将编辑服务拆分为本地或远程 C/S。

## 现有基础

当前架构已经具备命令驱动化的基础：

- `charme-core` 拥有平台无关的 `EditorCommand`；
- `EditorSession` 负责事务式应用、文档校验、revision、Undo/Redo 和 dirty 状态；
- `EditorSnapshot` 提供只读状态；
- Renderer 是文档的投影，而不是文档事实来源；
- 稳定 ID 可以避免命令依赖显示名称或 UI 控件位置。

后续应围绕这些能力增加统一的访问层，而不是让每种客户端直接操作内部数据。

## 统一交互模型

建议将接口分为三类：

```text
Command  修改文档或触发明确的编辑操作
Query    读取文档、选择、参数、诊断和渲染状态
Event    通知 revision、渲染完成、Shader 错误和其他异步结果
```

GUI、REPL、Lua、Python 和 AI 都应成为这一层的客户端。CLI 可以是人类可读的命令行外壳，也可以提供机器可读的结构化输出；AI 不应依赖解析人类格式化文本。

命令应表达业务意图，例如修改指定材质参数、绑定材质或重新加载 Shader，而不应表达“点击某个控件”或“按某个快捷键”。

## CAD 风格与模态交互

CAD 和模态文本编辑器具有相似的基本流程：

```text
选择对象 → 进入命令/编辑 → 提供参数 → 确认或取消
```

Charme 可以采用“弱模态”模型：

### 导航/选择模式

浏览角色、材质槽、材质、Shader 和参数；改变主选择或多选集；不直接修改数据。

### 命令模式

执行查询、修改参数、绑定材质、重新加载、保存、导出和渲染等操作。

### 编辑模式

编辑名称、路径、数值和文本内容。

### 多选/批量模式

对多个材质槽或材质执行统一操作，并将一次批处理作为一个 Undo 单元。

模式必须在界面中清晰显示，鼠标操作仍应可用，`Esc` 应有一致的取消/返回语义。应借鉴 Vim 的上下文和效率，但不应复制其隐晦的模式行为。

交互状态建议分为三部分：

```text
当前上下文  项目 / 角色 / 材质槽 / 材质 / Shader
选择集      主选择 + 多选对象
交互模式    选择 / 命令 / 编辑 / 脚本
```

不要将“当前选择”和“当前模式”混为一谈。

## C/S 方向

建议先建立逻辑上的 Server，再决定是否拆成独立进程或网络服务。

### 阶段一：进程内编辑服务

GUI、REPL 和脚本通过同一个编辑服务访问 `EditorSession`。此时不需要 IPC 或网络协议。

### 阶段二：本地 CLI 和脚本客户端

提供独立 CLI，用于打开项目、查询、修改、验证、保存和批量渲染。脚本和 REPL 使用相同命令。

### 阶段三：本地 C/S

在确有需要时引入 `charme-server`，由 GUI 和 CLI 通过 Unix socket 或其他本地 IPC 连接。Server 持有权威会话，客户端发送命令并订阅事件。

### 阶段四：远程服务

只有在远程渲染、多用户协作或外部自动化明确需要时，才考虑 TCP、HTTP 或 WebSocket 等网络协议。

完整 C/S 会带来协议版本、断线重连、并发 revision、路径权限和进程生命周期等成本，因此不建议一开始就引入网络层。

## 脚本语言选择

### 原生 DSL：REPL 和简单脚本

自定义 DSL 最适合 CAD 风格体验：命令短、面向项目概念、支持选择上下文、事务、查询和补全。初期不必做成完整编程语言，可以先支持命令、参数、变量、`include`、事务和基础错误处理。

DSL 是用户体验层，不应直接承担业务逻辑；它应被解析为统一的 Command/Query 调用。

### Lua：嵌入式脚本和插件

Lua 适合作为应用内高级脚本语言：体积小、启动快、部署简单、容易限制权限，也适合插件和批处理。它比 Python 更适合嵌入 Charme 或 Server。

Lua 不应直接暴露 Rust 内部对象，而应通过稳定的高层 API、稳定 ID 和受控能力访问文档。

### Python：外部自动化客户端

Python 适合复杂批处理、数据分析、AI、资产管理和外部工具生态。建议未来让 Python 作为外部客户端连接 Command/Query API，而不是第一阶段嵌入主程序，以避免运行时打包和跨平台发布复杂度。

### Ruby

Ruby 也适合构造 DSL，但目前在 Charme 的资产、AI 和数据处理场景中没有明显优势，暂不作为优先目标。

### 建议结论

```text
自定义 DSL  负责 CAD 风格 REPL 和便携脚本
Lua        负责嵌入式高级脚本和插件
Python     未来负责外部自动化和生态集成
Ruby       暂不支持
```

## AI Agent 集成

AI 应被视为一个受权限控制的特殊客户端，而不是模拟用户操作 GUI 或键盘。

推荐流程：

```text
查询状态 → 生成变更计划 → 用户确认 → 事务执行 → 观察事件
```

AI 可以查询当前项目、选择、材质参数、Shader 反射结果、诊断和渲染状态，然后发出结构化命令。命令应使用稳定 ID 或明确上下文，不能依赖列表位置。

AI 操作必须支持：

- 只读、编辑、文件访问等权限分级；
- `dry-run` 或变更预览；
- 批量操作确认；
- 单次计划对应一个事务和 Undo 单元；
- `expected_revision`，避免覆盖用户的新修改；
- 超时、取消和资源配额；
- 文件路径白名单；
- 审计日志和可追溯结果；
- 结构化错误与异步事件。

AI 可以生成 DSL 或 Lua，但默认应优先调用结构化 API；脚本执行仍必须经过权限、校验和事务边界。

## 设计原则

1. 命令表达意图，不表达 UI 操作。
2. 文档和 `EditorSession` 是唯一事实来源。
3. GUI、REPL、脚本和 AI 不实现各自独立的业务逻辑。
4. 人类可读输出和机器可读输出分离。
5. 所有批量修改都应可预览、可撤销、可审计。
6. 稳定 ID 优先于显示名称；名称只作为用户便利语法。
7. 先定义本地、稳定的命令语义，再选择 IPC、网络或脚本运行时。
8. 先实现脚本和命令接口，再决定是否拆分完整 C/S。

## 待确认问题

- 原生 DSL 是主要用户接口，还是仅作为辅助控制台？
- Server 是否需要支持多个同时连接的客户端？
- 是否需要远程渲染或远程项目会话？
- Lua 是内置功能，还是作为插件系统的后续能力？
- AI 默认是否必须经过用户确认，哪些操作可以自动执行？
- 命令协议是否需要从第一天就支持机器可读格式和版本协商？
